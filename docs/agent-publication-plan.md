目的：在同一仓库内，把现有通用角色分别补齐为有输入、决策、方法消费和结果证据的案例，再按角色独立提交、推送及核验。各角色的基础文档已经公开；本轮是完善案例，不是首次发布角色或创建多个仓库。

目标仓库：Lanqiao-Luca/ai-java-workflow，分支main。基线提交：e17c1801dc46234e221ccc9c264ccdf35aa88adc。保留实现者及书签Java示例；仅使用当前公开内容和独立新写的虚构材料。原私有框架不读取、不修改；私有审计、凭证、个人路径与真实业务数据不纳入。

本文件先于后续案例写入保存。文档状态、公开提交和真实运行分别记录；一个文件存在或字段齐全不证明业务语义正确。

## 执行顺序与逐项产物

| 顺序 | 已有Agent | 本轮完善重点 |
| --- | --- | --- |
| 1 | requirement-analyst | 澄清目标、已决/未决、可观察验收与可实施范围 |
| 2 | verifier | 验收到断言、实际检查、失败复现及未运行边界 |
| 3 | code-reviewer | 冻结差异、可复核发现、原作者修订与定向复核 |
| 4 | semantic-reviewer | 需求到实现、实现反查需求与边界反例 |
| 5 | principle-reviewer | 适用原则、正反证、违反与缺证分开 |
| 6 | diagnostician | 竞争解释、区分性证据、限定结论与下一步 |
| 7 | query-reviewer | 查询语义、静态性能风险、结构缺口和测量建议 |
| 8 | delivery-planner | 真实完成依据、依赖、未决、停止与接续 |
| 9 | document-reviewer | 逐要求内容验收、引用、能力状态与修订复核 |

每项包含：完整角色合同、对应Skill的案例入口、独立案例目录中的任务声明、README、trace、具体分析产物或虚构夹具、result和文件身份清单。必须实际说明输入如何影响选择、Skill如何消费Standards、产物能支持哪些结论、失败时在哪里停止。不能只增加导航、空表或声称角色已自动运行。

## 每项怎样执行

1. 接收一个独立变更包，确认它只修改本角色、相交Skill入口和新增案例；保护已有改动。包外材料不自动纳入。
2. 检查全部待公开字节、路径、来源与引用。案例独立虚构；不复制内部规则、服务坐标、日志、账号或私有工具。共用Skill已有案例入口保留，不覆盖其他角色的结果。
3. 按当前包完善角色及案例，更新public-manifest.json；案例identity清单覆盖全部案例文件，清单自身除外。案例引用须成立，不依赖本机路径。
4. 执行文档清单/链接/合同检查和通用案例结构/身份检查；再人工审阅输入、决策、证据与结论的含义。脚本只证明声明结构与字节身份，不能代替语义审查、版权判断或真实业务运行。
5. 核实际差异、隐私边界和git diff --check。仅显式暂存本包及相交入口/清单；一个角色一个提交，不混入下一个包。
6. 普通push到main，读取远程ref及提交树核SHA与实际文件。结果未知先查远程，不重复创建提交或使用force。
7. 远程证据写入发布结果记录；本项完成后再进入下一项。问题定向修复和复核，失败不伪记完成。

通用检查器、计划及目录支持可先单独提交。最后根据真实内容更新首页、角色目录和结果记录；不在同一提交中写它自身的哈希。
