# 完整虚构案例：书签显示名的整改收敛

这是独立编写的控制教材，使用虚构候选名、发现和时间；没有从真实业务记录改名生成。它不改动已有 Spring 案例的源码或历史证据。

## 目标与角色

假设一个 Java/Spring 书签服务要规范化显示名，必要验收有三项：非空名称保存、纯空白拒绝、未授权不写入。已有研发 Workflow 承担实现、验证和审查；Loop 只决定是否继续和停止。调用方为此教材选择最多2轮、累计60秒、模拟时钟1060截止；这些数值不是框架默认值。

## 一条接续链

| 阶段 | 模拟事实 | 离线控制结果 |
| --- | --- | --- |
| 第1轮验证/审查 | candidate-a 仅两项验收满足，F-1 指出空白名称遗漏；下一最小动作是修校验 | NEXT_ROUND，保留原发现并交 Workflow 实现阶段 |
| 第2轮整改后的冻结点 | 当前 candidate-b，证据仍属于 candidate-a；原轮数已耗尽 | HOLD，旧证据不能关闭发现；不再启动第三轮 |
| 同第2轮已有复验回执 | 在额度内完成的 candidate-b 全部验收与责任复核已到，F-1 关闭 | DONE，仅结束整改控制，回 Workflow 交付阶段 |

第二行和第三行是同轮 Workflow 中的冻结核对与既有结果核对，不新开一次整改；若当时尚未执行复验且需额外一轮或已过时间额度，则保持 STOP/未完成，不能拿第三行的模拟回执当实际补证。

[机器可读情景](review-trace.json)明确每步输入；检查器逐步执行同一判定参考，核旧预算未清零、候选变化未用旧证据完成。对照情景还会把发现保持开放、删除必要验收、取消授权、保留未知副作用、耗尽时间或不提供下一有效动作，确认不会获得新的执行许可。

## 运行与交付

从仓库根运行 `python3 -B scripts/check_loop_cases.py`，只需 Python 标准库。没有真实 Agent、Spring 构建、数据库、提交或部署；结果是离线控制边界的实际测试，不是本虚构需求已在运行系统实现。

模拟链最终交付候选与验收集合、原发现关闭依据、累计预算和后续责任。若失败则交残余、最早恢复点及触发条件，不能承诺后台继续。原生调度器的自动整改接线仍未实现。
