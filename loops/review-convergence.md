# 审查整改的有界收敛

目的：让真实发现驱动最小整改与复验，避免无限“再审一次”或把局部通过改写成全目标完成。

## 适用条件

同一研发目标已经出现具体发现或必要证据缺口，且本轮写集、接收职责、有限轮数和时间预算清楚。普通单次审核无需新建循环；技术故障另按[技术重试](technical-retry.md)计数，两者共享上层剩余时间，不能嵌套领取额外额度。

## 输入

沿用现有项目主记录，填[收敛空表](templates/review-convergence.md)：目标与完整验收集合、候选身份、发现ID、适用规则、证据版本、已消费轮次、累计时间、绝对截止、已受理动作、最早失效阶段和下一有效动作。首次验证/审核计第一轮，失败也占轮次；等待结果计时，离线交接不清零累计或顺延截止。

## 操作步骤

1. 调用方核当前授权、候选、原发现和预算，登记一次轮次，再交[研发 Workflow](../workflows/java-spring-development.md)完成适用阶段。
2. Workflow 按需交实现、验证和审查职责，返回当前候选上的真实结果。整改者的“已修复”不直接关闭发现，需验证/审查责任方复核。
3. 全部必要验收和原发现关闭都有当前适用证据时，结束此 Loop，回原 Workflow 的交付阶段。测试通过不等于 GitHub 已推送或生产已验收。
4. 候选、规则或共享输入变化时先标出受影响证据，从最早失效阶段复验；未受影响部分可复用。新候选不能清空原发现、轮次或副作用记录。
5. 仍有具体最小修复、可区分假设的新验证或必要补证，且预算/权限允许时才继续。反复读取同一结论不算进展；先重估低成本有效路径，没有则停止并交接。

## 输出与角色职责

本方法要求调用方记录 DONE、NEXT_ROUND、HOLD 或 STOP，以及对应理由、残余和接收方。离线参考函数仅返回状态字符串，理由及真实交接记录由调用方保存。Graph 仍负责整体目标与跨 Workflow 依赖；Loop 不直接启动 Agent、Skill 或工具，不另造问题池。调用方保存真实计时和计数；每个 Workflow/Agent 对其返回证据负责。

[原生 Workflow](../workflows/native-java-spring.md)当前失败仍停止，采用本方法需由当前调用方显式接续，本批次没有新增自动整改、恢复入口或后台调度。

## 验收方法

先读[完整虚构案例](examples/review-convergence.md)，运行 `python3 -B scripts/check_loop_cases.py`。参考判定覆盖陈旧证据、缺验收、发现未关闭、无进展、到限与候选变化后预算保持。此运行只校模拟事实的控制裁决，不实际调用模型、编译 Spring 或证明外部业务成功。

## 异常与停止

权限缺失、无有效下一步或预算耗尽时保留未完成；未知副作用先交接查原结果，不重放。截止后不能启动新动作；预算内已取得且仍适用的完整证据可作一次不新增执行的完成判断。超过预算才取得的证据不得据此报合规完成。

恢复先核身份、实际副作用和最早失效阶段；沿用旧发现与消耗。原额度已尽必须有调用方权限内明确的新预算及调整来源，不能通过换窗口、改候选或换工具刷新。局部等待只冻结相交部分，其他独立获准工作可以继续。
