**目的**：按必要上下文负担切分可验证执行单元，同时保全原目标与整体验收。

**适用于**：供当前方法的责任 Agent、作者与审查者使用；编制方案、展开下一阶段或执行中新增依赖时，当前材料可能挤占行动和验证空间。

# 按上下文负担拆解执行单元

## 适用条件

编制方案、展开下一阶段或执行中新增依赖时，当前材料可能挤占行动和验证空间。

## 输入

原目标与完整验收、全局约束、已有效材料、必要依赖、工具输出限制及当前恢复点。

## 操作步骤

先保全原目标和验收映射，再估计必需规则、输入、动作返回、验证及余量；没有可信限制时写未知，不编造固定 token 上限。材料反复截断、依赖扩张或一步无法明确输入输出时先拆分。

沿可验证产物、依赖、写集和恢复点划分单元；紧耦合约束保留在同单元或明确集成验收。总方案保目标覆盖和依赖，只展开当前就绪单元，不提前读取后续全部细节。

每个单元给目的、必要来源与读取条件、实际责任和动作、预算依据、产出与验收、失败和下一消费者。原合同要求全文读取的必要部分不能因拆解删除；若仍需加载所有兄弟单元则继续调整边界。

执行与接续沿[执行记录合同](execution-records.md)，保持原 run、累计预算、已完成前缀和未决。拆文件不会自动释放已加载上下文，也不自动授权新聊天、子 Agent 或后台流程。

## 输出

短总方案、原验收到单元的覆盖、当前就绪单元及最小读集、恢复条件与预算未知。

## 角色职责

责任 Agent 决定单元边界，Skill 适配到现有计划；不为拆分新建框架层级。

## 验收方法

代表单元可以仅凭其允许读集确定动作和验收，原目标完整且整体验收仍在。静态结构、实际执行与效果收益分别验证。

## 异常与停止

不可再分的必要合同仍无法容纳时，保最小阻塞和可行接续条件，不删要求求通过，不无限递归拆成无实质产出的碎片。
